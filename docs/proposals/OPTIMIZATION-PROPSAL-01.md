# Анализ встроенной СУБД XdStorage

> **Архитектурный разбор:** [OPTIMIZATION-PROPSAL-01-ANALYSIS.md](OPTIMIZATION-PROPSAL-01-ANALYSIS.md)
> (2026-10-23) — каждое направление сопоставлено с планом (FP-9/FP-3/W-4b/W-4d/FP-13);
> в поезд 2.1.0 добавлена задача 33 (замер serialized-доли cold-путей — gate для FP-9).

**XdStorage** — это встроенная (embedded) объектная СУБД для Java, работающая с графами обычных POJO/JavaBeans. Её главная особенность — работа без сервера, отсутствие нативного кода, поддержка ACID-транзакций, MVCC, индексов и триггеров. Данные на диске хранятся в человекочитаемом формате (YAML или XML), а целевой масштаб базы составляет до пары гигабайт (10⁴–10⁵ объектов).

---

## 1. Сравнение с популярными аналогами

Поскольку XdStorage является встроенным решением, его целесообразно сравнивать с базами аналогичного класса.

| Критерий | **XdStorage** | **H2 / SQLite (Встроенные реляционные)** | **MapDB** | **EclipseStore** | **RocksDB** |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Модель данных** | **Граф POJO/JavaBeans** | Реляционная (Таблицы) | Key-Value (Map / Set) | Нативный граф объектов Java | LSM Key-Value (набор байт) |
| **Транзакции** | **ACID 2PC, MVCC снапшоты** | Полный ACID | Опциональный ACID | Отсутствуют (ленивое сохранение) | Только атомарные батчи |
| **Что нужно писать самому** | **Ничего** (аннотации на POJO) | Схему таблиц + маппинг (ORM/JDBC) | Сериализацию, индексы, запросы | Индексацию и движок запросов | Весь слой объектов, индексов и запросов |
| **Формат на диске** | **Текстовый (YAML, XML)** | Бинарный | Бинарный | Бинарный | Бинарный (SST-файлы) |
| **Зависимости** | **Только Java** (нет нативного кода) | Только Java | Только Java | Только Java | Требует нативные библиотеки (JNI) |
| **Потолок по записи** | **~3k–9k tx/s** (версия 2.1.0) | Высокий | Очень высокий | Высокий | Экстремально высокий |

### Где XdStorage выигрывает:
* **Нулевой бойлерплейт:** Разработчик просто размечает доменные модели аннотациями. Нет необходимости подключать тяжелые ORM (например, Hibernate) и настраивать маппинг в таблицы.
* **Прозрачность для SRE/DevOps:** Данные хранятся в обычных текстовых файлах. Их можно просматривать через `cat`, фильтровать с помощью `grep`, проверять изменения через `git diff` или делать бэкап базовой командой `cp -r`.
* **Продвинутый функционал «из коробки»:** Для встраиваемой базы наличие MVCC, неблокирующего чтения, вторичных индексов и триггеров прямо внутри коммита является серьезным преимуществом.

### Где XdStorage проигрывает:
* **Производительность записи:** Из-за текстового формата (YAML/XML) и архитектуры перезаписи B+деревьев поисковых ключей база значительно медленнее сырых Key-Value хранилищ вроде RocksDB.
* **Отсутствие SQL:** Нет поддержки классических соединений (joins), агрегаций и аналитических функций. Запросы строятся исключительно на Criteria API.
* **Эксклюзивный доступ:** Исключена параллельная работа двух процессов приложения с одной папкой данных (выставляется монопольная файловая блокировка).

## 2. Направления ускорения и повышения производительности

Разработчики проекта открыто признают проблемы с пропускной способностью записи (Write Throughput) и уже начали оптимизацию (в версии 2.1.0 добавлено журналирование индексов). Опираясь на архитектуру базы, можно предложить следующие фундаментальные шаги для повышения производительности:

### Введение бинарного формата сериализации (Pluggable Formats)
Текущее использование YAML и XML создает избыточную нагрузку на CPU и память при парсинге текста.
* **Решение:** Добавить плагин для бинарных форматов хранения (например, **Protocol Buffers**, **Kryo**, **CBOR** или **MessagePack**). Это уменьшит размер файлов на диске, снизит нагрузку на Garbage Collector (GC) и ускорит чтение/запись в 5–10 раз.

### Оптимизация работы с диском (Write Path & Journaling)
Полная защита от потери питания (`durableWrites(true)` через жесткий `fsync`) замедляет запись почти в 100 раз. Также узким местом остается перезапись B+деревьев поисковых ключей при обновлении данных.
* **Группировка фиксаций (Group Commit):** Реализовать механизм, объединяющий несколько параллельных транзакций в одну дисковую операцию записи журнала (WAL/Journal).
* **Переход на LSM-структуры для индексов:** Вместо B+дерева, требующего частой перезаписи блоков, использовать концепцию LSM (Log-Structured Merge-tree) для индексов. Это превратит случайную перезапись поисковых ключей в быструю последовательную запись в конец файла.

### Кэширование и управление памятью (Heap Management)
По документации, каждый объект в памяти (working-set) забирает около 1.4–2 КБ Heap. При росте базы это неизбежно приведет к деградации производительности из-за пауз очистки памяти (GC Pauses).
* **Off-Heap кэширование:** Вынести кэш индексов или часто читаемых сериализованных объектов за пределы Java Heap (используя `Static/Direct ByteBuffers` или Foreign Function & Memory API), как это реализовано в MapDB или Chronicle Map.

### Генерация кода на этапе сборки (Build-time Codegen)
Сейчас для генерации рантайм-оберток XdStorage жестко требует полноценный JDK внутри контейнера, так как код создается на лету.
* **Решение:** Реализовать APT (Annotation Processing Tool) или плагин для Maven/Gradle, чтобы прокси-классы и методы сериализации генерировались **на этапе компиляции**. Это устранит оверхед на рефлексию при старте, снизит потребление памяти и позволит компилировать приложение в нативный образ (GraalVM Native Image).

### Параллельное выполнение триггеров
В текущей реализации триггеры выполняются строго синхронно внутри фазы коммита транзакции.
* **Решение:** Разделить триггеры на синхронные (критичные для транзакции) и асинхронные. Асинхронные триггеры должны отправляться во внутреннюю очередь (например, RingBuffer / Disruptor) и обрабатываться фоновыми потоками, не блокируя основной поток записи.
